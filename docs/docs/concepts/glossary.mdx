# Glossary

| Term | Meaning |
| --- | --- |
| User | The person for whom a personal agent acts. |
| Personal Agent | Software acting for one user when interacting with a company. |
| Company | An organization publishing PAP discovery and one or more interaction paths. |
| `poppy.json` | The discovery document at `/.well-known/poppy.json`. |
| User ID | A stable, opaque identifier for one user at one company issuer, assigned by the personal agent. It is not PII. |
| Agent ID | An optional, stable, opaque identifier for one of a user's agents at one company; it names no separate party. |
| Session | One user's activity at one company through one personal agent, named by a random `sid` the personal agent chooses. |
| Session header | The `Poppy-Session` header: a JWT the personal agent signs for each request, naming the Session and the User ID. |
| Delegated key | A short-lived key a personal agent signs its Session JWTs with, one for each User ID. |
| Delegation | A JWT of at most 24 hours, signed by a key in the agent's `jwks_uri`, that vouches for a delegated key. It names no User and no company. |
| Refresh token | A long-lived OAuth credential from a sign-in, used only at the company's token endpoint. It isn't tied to a Session. |
| Access token | A short-lived OAuth credential for an account. A Session is signed in on each request that carries one. |
| Scope hints | Per scope, what its most consequential operation `changes` and whether it touches `personal_data` (`auth.scope_hints`). |
| Excluded task | A task the company chose not to offer through the protocol, with an optional alternative. |
| Company Agent | The company's conversational agent advertised by discovery. |
| Operation | An action the company performs once the user approves one revision of its exact terms. |
| PAP extension | An optional, wire-negotiated capability such as `operations`. |
| Reactor extension | A package of runtime plugins that can contribute SDK behavior. |

## OAuth terms

PAP uses OAuth's own names for its tokens: refresh token and access token.
(Earlier drafts called them Account Token and Session Token.) It names a few
other things for what they do, because they are narrower than the OAuth terms:

| PAP term | OAuth term | Why the PAP name |
| --- | --- | --- |
| User ID | Pairwise subject identifier, `sub` in the Session JWT | The personal agent assigns it, not the company's OAuth server as in OpenID Connect. |
| Sign-in | User authorization | It names the user's approval of the agent's access, whatever the flow. |
| Sign-out | Revoking the refresh token | It is the user ending the agent's access to their account; the Sessions continue signed out. |
| Signed out | Pseudonymous | The company recognizes the user by User ID but doesn't know who they are. |

DPoP ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)) is a company's choice,
as in OAuth, and personal agents SHOULD support it. These SDKs don't send DPoP
proofs yet, and refuse a `DPoP` token type.

The upstream specification is authoritative when terminology here and the
[draft specification](https://personalagentprotocol.org/docs/0.3/spec#terms) differ.
