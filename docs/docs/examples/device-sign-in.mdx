# Device Sign-In

<Deck spec={deck} />

The paired examples use the real SDK state machine against a deterministic
company transport. They demonstrate a terminal-style personal agent that
cannot receive a browser callback.

```mermaid
sequenceDiagram
  autonumber
  actor User
  participant Tool as Read-only agent tool
  participant SDK as DeviceSignInClient
  participant Company
  participant Vault as Reactor stores
  Tool->>SDK: Begin for the scopes it needs
  SDK->>Company: Request device authorization
  Company-->>SDK: Link, user code, interval, private device code
  SDK->>Vault: Save private device code
  SDK-->>Tool: Link, user code, opaque reference
  Tool-->>User: Authenticate on company page
  SDK->>Company: First poll, with a fresh client assertion
  Company-->>SDK: authorization_pending
  SDK->>Company: Poll at interval
  Company-->>SDK: slow_down
  Note over SDK: Increase interval by five seconds
  SDK->>Company: Poll at new interval
  Company-->>SDK: Access token + refresh token + partial scopes
  SDK->>Vault: Store the refresh token
  SDK-->>Tool: Safe lifecycle evidence + opaque token reference
```

The model sees that the link and code were presented, early polling was
suppressed, pending and slow-down responses were respected, every network poll
carried a fresh client assertion, and one requested scope was omitted. The sign-in
names no Session: any Session is signed in by sending the access token. The link is
shown only because its host is the issuer's or one of the issuer's
`protected_resources`. It never sees the device code, assertions, or tokens.
