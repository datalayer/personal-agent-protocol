# Mediated Sign-In

<Deck spec={deck} />

Some companies can't offer Direct or Device Sign-In yet. They declare the fields
they need in the `mediated-sign-in` extension, and the personal agent sends what
the user types to the issuer's token endpoint, as an OAuth extension grant. It is
the one sign-in where a password passes through the agent's host, so the SDK narrows what the
host can do with it. The paired examples run the real `MediatedSignInClient`
against Manzanita Outfitters, which asks for an email, a password, and then a
one-time code. Mediated Sign-In is transitional, like OAuth's password grant:
a company offers it only until it can add Direct or Device Sign-In, and the
protocol plans to remove it at a date set with version 1.0.

```mermaid
sequenceDiagram
  autonumber
  actor User
  participant Tool as Agent tool
  participant SDK as MediatedSignInClient
  participant Input as pap.protectedInput (host surface)
  participant Company as Company token endpoint
  Tool->>SDK: sign_in(company, client_id, scopes)
  SDK->>SDK: Extension and grant offered, field names allowed? Otherwise refuse before asking
  SDK->>Input: Ask for Email and Password for manzanita.example
  User->>Input: Types them (never into the chat)
  SDK->>Company: POST the grant once, with a client assertion, no redirect followed
  SDK->>SDK: Drop the values
  Company-->>SDK: 400 code_required, sign_in_id, sent_to, expires_in
  SDK-->>Tool: code_required + opaque reference + sent_to
  Tool->>SDK: submit_code(reference)
  SDK->>Input: Ask for the code
  User->>Input: Types the code
  SDK->>Company: POST the grant with sign_in_id and one_time_code only
  Company-->>SDK: The token response: access token, refresh token
  SDK-->>Tool: complete, granted scopes, refresh token reference
```

The walkthrough also shows the refusals:

- A field named like a parameter of the grant, such as `client_id`, is
  `invalid_mediated_extension`, raised before the user is asked anything.
- The protected input must answer exactly the declared fields, none empty.
- Only the `client_id` that started a sign-in can finish it: the company answers
  anyone else `invalid_grant`.
- A wrong code is `code_required` again with the same reference; the company
  ends the sign-in with `invalid_grant` after its attempt limit.

The model sees field labels, which fields are secret, the company's domain,
the masked destination of the code, statuses, and granted scopes. The
credentials and the code exist only in the host's protected input and in the
one token request; the access and refresh tokens stay in Reactor stores.

TypeScript: `new MediatedSignInClient({ reactor, fetch })` with `signIn()` and
`submitCode()`, the trusted surface contributed at `ProtectedInputs`.
