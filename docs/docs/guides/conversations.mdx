# Conversations

A PAP conversation is how a personal agent talks to a company's agent (draft
0.3 §8). `ConversationClient` sends idempotent messages and reads an ordered
event log by long polling (see [conversation messages](/examples/conversation-messages/)
and [conversation events](/examples/conversation-events/)). This guide covers
streaming and the controls: sign-in mid-conversation, Direct Conversations,
handoff, and closing.

## Streaming over SSE (§8.6)

```python
async for item in conversations.stream(endpoint, conversation_id, session=session):
    if isinstance(item, TextDelta):
        ui.show_typing(item.message_id, item.text)   # display only
    elif isinstance(item, StreamReconnected):
        ui.drop_partial(item.discarded_message_ids)
    else:
        handle_event(item)                           # the ConversationEvent to act on
```

```typescript
for await (const item of conversations.stream(endpoint, conversationId, { session })) {
  if ('kind' in item && item.kind === 'text-delta') ui.showTyping(item.message_id, item.text);
  else if ('kind' in item && item.kind === 'reconnected') ui.dropPartial(item.discardedMessageIds);
  else handleEvent(item);
}
```

- **Deltas never act.** `TextDelta.actionable` is always false. The complete
  `message` event replaces the pieces; route deltas to display only.
- **Reconnect from `Last-Event-ID`.** When the company ends the stream before
  the conversation closes, the client reopens it from the last event handled
  and yields `StreamReconnected`. Pieces of a message whose complete event did
  not arrive are listed as discarded.
- **No duplicates.** Replayed events are suppressed by ID, in a bounded set
  that fails closed (`event_history_too_large`).
- **Bounded.** `max_reconnects` reconnects in a row without a new event end in
  `stream_unavailable`. A company that answers JSON instead of
  `text/event-stream` is `sse_unsupported`: use `events()`.
- The iterator ends on a `state` event with `closed`.

## Sign-in mid-conversation (§8.11)

When the company needs the user's account, or more scopes, it adds an
`authorization` event: `error` is always `insufficient_scope`, with the same
meaning as the API error, and `scope` always names the scopes needed. The host
responds as it would to that error, with a refresh token that covers the scopes
or by running a sign-in mode the company offers, then keeps sending to the
**same conversation ID** in the **same Session** (the same `sid`) with the new
access token. Nothing in the conversation is restarted; the model never sees the
sign-in's codes or tokens.

A conversation isn't tied to one access token or even one Session: the agent
may switch tokens partway, after signing in, refreshing, or signing out, or
continue in a new Session, as long as the request matches the conversation's
owner (§8.2): the agent's `client_id` and the User ID that started it, and,
once it uses the user's account, that account too; Agent IDs are not part of
it. Before it uses an account, any token of the same agent and user continues
it, and the conversation then uses that account. After it uses account A, the
same agent and user signed out get a challenge (`insufficient_scope`; the
conversation stays open, so the user can sign in again and continue it),
signed in to another account `conversation_not_found`; another User ID or
another agent is always `conversation_not_found`.

## Direct Conversations (§8.10)

`start_direct(endpoint, parent_id, message)` (`startDirect` in TypeScript)
opens a conversation under an open parent for the user to talk with the
company through the agent's interface. Only the personal agent starts one.
While it is open, the parent refuses messages and handoff with
`direct_conversation_open`; the client exposes the open conversation's ID in
`error.details["conversation_id"]` so the host can route the user there. The
parent receives `direct_opened` and `direct_closed` events.

The parent must be open, the caller's own, not a Direct Conversation itself,
and without an open Direct Conversation; each failure has its own code:
`conversation_not_found`, `conversation_closed`, `invalid_request`, and
`direct_conversation_open`.

**When the company asks.** A `user_requested` event in the parent, with its
`reason`, is an invitation: the agent asks the user, and when they agree calls
`accept_user_request(endpoint, parent_id, event_id)` (`acceptUserRequest` in
TypeScript), which sends the parent's ID and the event's and no message, so
the company speaks first. Its first message is read with `wait` on that call,
or by reading or streaming events. The same call again, with the same parent
and event, returns the same Direct Conversation with no message added, even
once it closed; an event that is not a `user_requested` event of the parent is
`invalid_request`. The `reason` stays an invitation, not the first message. If
the user declines, the agent says so in the parent conversation.

Either party may close a Direct Conversation, the company after inactivity;
closing the parent closes it too. The agent may observe every message in it,
and the company sends nothing there that it cannot share with the agent.

## Handoff (§8.9) and closing (§8.12)

`handoff()` asks for a person at the company: the conversation is `queued`,
then `responder` becomes `human` when someone takes it, or the company says
none is available and its agent continues. `close()` ends the conversation;
the company refuses later messages with `conversation_closed`. Closing does
not cancel anything the conversation started, such as an order or a return.

## Who wrote each message: `author`

Every message names its `author` (§8.4): `type` is `agent` or `human`, and a
company's message may add who, with `id`, display `name`, and `image` (an
HTTPS URL) for its person or AI persona. The personal agent never sends those
three: its own messages are `Message(id=..., author=Author(type="agent"), ...)`,
or `human` for the words a person typed themselves in a Direct Conversation. A
company built with the SDK writes its people's replies with
`staff_reply(..., author_id=..., author_name=..., author_image=...)`.

## Extension content in messages

Content an extension defines travels in a message's `extensions`, keyed by the
extension's name (spec 8.4): the Operations extension's `operation` and
`approval` in `extensions.operations`, the pages a company message refers to in
`extensions.links` (the Links extension, version 1), and the notices it marks
apart, such as an allergen warning, in `extensions.disclosures` (the
Disclosures extension, version 1). A message needs `text`, `data`, `context`
or `extensions`.

- Python reads them as properties: `message.operation`, `message.approval`,
  `message.links` (`Link`: `url`, `title`) and `message.disclosures`
  (`Disclosure`: `text`); a personal agent approves with
  `Message(..., extensions=operations_content(approval=approval))`. TypeScript
  reads them with `messageOperation`, `messageApproval`, `messageLinks` and
  `messageDisclosures`, and builds the approval with
  `operationsContent({ approval })`.
- Both SDKs check the three extensions' content by its shape (`OperationsContent`
  carries one of `operation` and `approval`; a link's `url` is HTTPS) and keep any
  other extension's content as the object it is.
- A side sends an extension's content only to a side that lists the same
  version. The reference companies send links and disclosures when
  `CompanyConfig.links` and `CompanyConfig.disclosures` are set (Manzanita sets
  both) and the agent's client metadata lists the extension; without the
  Disclosures extension the notice goes in `text`, and without Links the page is
  left out. A personal agent lists what its host can show
  (`AgentIdentity(extensions=("operations", "links", "disclosures"))`).

## Who wrote each reply: `PapReplies`

A company's message is written by its agent or by one of its people
(`author`), apart from where the conversation stands (`status`) and who
answers it now (`responder`). A host shows them apart with `PapReplies`
(`personal_agent_protocol.ui`), of type
`application/vnd.datalayer.pap.replies+json`, version 4, made with
`PapReplies.of(company, conversation_id, messages, status=..., responder=...)`
from the messages a page of events carried.

- It names the conversation the replies are in (`conversation`): where the
  person's own words open a Direct Conversation under it, typed on the page
  and sent as theirs (`author.type: human`), never through the model. Version
  1 named none.
- Each reply says who wrote it (`author`: `agent` or `human`) and, when the
  company gave one, the writer's `name` (version 3), shown as *one of its
  people (Rosa)*.
- Each reply carries the pages it refers to (`links`, each a `url` and a
  `title`; a page shows the title with the URL's host, `PapLink.host` or
  `papLinkHost`, never the title alone) and the notices it marks apart
  (`disclosures`, shown in full, apart from the text), version 4. Without the
  extensions both are empty.

- Only the company's own messages with text are replies, each verbatim; a
  message carrying only data is the model's to read. With none, `of` returns
  `None` and nothing is drawn.
- `text()` says each on its line: *shop.example, its agent: …* or
  *shop.example, one of its people: …*, then each notice (*Notice: …*) and each
  link with its host (*Link: Return policy (shop.example)*).
- The personal agent's own messages are `author.type: agent` (PAP-8.8-01): only
  what the person typed themselves, in a Direct Conversation, is `human`.

The TypeScript SDK types it (`PapRepliesData`) and checks it with
`isPapReplies`, against the committed example
`protocol/fixtures/pap-replies-display.json`.

## Security boundary

- Access tokens, delegated keys, Session JWTs, pairwise IDs, and cursors stay in
  the host.
- A model receives the event fields it needs: company text, data, event types,
  and statuses. It never treats conversation text, from either side, as the
  user's approval of anything.
- Errors carry codes (and, for `direct_conversation_open`, a validated
  conversation ID), never response bodies.

See the runnable [conversation streaming](/examples/conversation-streaming/)
and [conversation control](/examples/conversation-control/) examples, and the
upstream [conversations specification](https://personalagentprotocol.org/docs/0.3/spec#conversations).
