# Operations

The Operations extension (version 2) gives actions an exact, durable approval,
and adds no endpoints. A company that wants the user's approval refuses the
request for the action and returns the operation: the terms, in plain language
and as JSON. The personal agent gets the user's approval and makes the same
request again with it. The company checks it, performs the action at most once,
and responds as it would have without operations.

| Interface | The operation arrives as | The approval goes back as |
| --- | --- | --- |
| API | HTTP 403 with `error: approval_required` and `operation` | The same request with the `Poppy-Approval` header |
| MCP | An error result with `structuredContent.operation` | The same call with `_meta["personalagentprotocol.org/approval"]` |
| Conversation | A company message's `operation` | A message with `approval` |

An operation is `operation_id`, an opaque `revision`, `summary`, optional
`terms`, and `expires_at`. It has no state, no URL, and no result: the answer to
the approved request is the result.

## Negotiate

```python
from personal_agent_protocol import OperationsClient, operations_negotiated

negotiated = operations_negotiated(discovered.document, my_client_metadata)
if not negotiated:
    ...  # one side doesn't list operations version 2: the company handles approval itself
operations = OperationsClient(reactor=reactor)
```

A company that needs the extension answers an agent that doesn't list it with
`extension_required`, and an MCP tool with an ordinary tool error. Another major
version doesn't count as support.

## Ask the user, then send the same request

```python
approval = await operations.ask_user(
    operation,
    organization=organization,          # the company's name and domain, shown with the summary
    tenant_id=tenant_id,
)
sent = await operations.send(
    lambda approval: api.call(
        "POST", url, session=session, token=token, body=body, approval=approval
    ),
    approval,
)
```

```typescript
const approval = await operations.askUser(operation, { organization, tenantId });
const sent = await operations.send((approval) => api.call("POST", url, { body, token, approval }), approval);
```

- `ask_user` goes through the host's own approval surface
  (`pap.approvalSurface`, an `ApprovalSurface`). It is asked about every
  operation, with the company's name and domain, the `summary` as the company
  wrote it, `expires_at`, and any difference the terms check found. Only `True`
  from the surface approves; anything else is `not_approved`, and a host with no
  surface can't approve at all (`no_approval_surface`).
- Nothing approves on the user's behalf, even when they said they would approve
  something like it. A company that lets users allow an action in advance doesn't
  return an operation for it.
- Text from the company is never the user's approval, and in a conversation only
  a message's `approval` approves, whatever its `text` says.
- Save the request that returned the operation, and send exactly that. Don't
  have the model write it again.

## Check the terms

`terms_differences(operation, asked)` compares the terms with the summary, since
the company writes both, and with what you asked for: `asked` maps a dotted path
in `terms` to the value you expected. `ask_user(asked=...)` passes what it finds
to the surface, to point out to the user.

```python
terms_differences(operation, {"order_id": "ord_7Hk2", "price_difference.currency": "USD"})
```

## A new revision

An approval covers one revision. When terms change the company returns the same
`operation_id` with a new `revision`, and asks for approval again. If an
approval's revision can't be accepted (one it never returned, one past its
`expires_at`, one for another request), the company performs nothing and returns
a new revision: never the one named, so a retry can't loop. `send` reports it as
`new_revision`; show what changed (`ask_user(replaces=earlier)`) and ask again.

## Retries, at most once

`send` keeps the same approval after a failure, a timeout, or a `503`, waiting for
`Retry-After`. The company answers a repeat with the original response, and `503`
with `Retry-After` while the action is being performed or its outcome isn't known.

When a retry gets a new operation, or no answer comes in the end, `sent.status`
is `unknown`. Don't ask the user to approve the same action again until you know
whether the first was performed: find out another way, such as from the order in
the company's API. An `Idempotency-Key` doesn't carry over to the request with
the approval.

## For a company

An API or tool returns `ApiResult(operation=ProposedOperation(...))` or
`ToolResult(operation=...)`, and a `CompanyAgent` a `Reply(operation=...)`, without
acting. `action` names the `pap.company.operationExecutor` that performs it, and
with `subject`, what it is done to: requests for the same action and subject are
one operation.

The service does the rest, in the extension's order: the Session can approve it,
it hasn't been performed already, and the revision is one it returned, unexpired,
for exactly this request. An operation returned signed out can be approved only
in that Session. One returned signed in can be approved in any Session of the same
personal agent and user signed in to that account; a signed-out Session of theirs
gets the challenge, and anyone else's request is handled as if it had no approval.

The executor returns an `ActionResult`, raises `OperationFailed` with what changed,
or `OperationOutcomeUnknown` while it isn't known whether it took effect, which
retries answer with `503` until `settle`. `revise` replaces the terms, withdrawing
the earlier revisions. The record keeps the approval: the revision and the time.

## Show what is asked: `PapConfirm`

A host that asks the person in a page, not only in its own interface, sends
the operation as a [Reactor](https://github.com/datalayer/reactor) display:
`PapConfirm` (`personal_agent_protocol.ui`, the `ui` extra), of type
`application/vnd.datalayer.pap.confirm+json`, version 2. An MCP tool puts it
in its result's `_meta["reactor.ui/display"]`; any page with a renderer for
the type draws the card, and a page without one shows its text.

```python
from personal_agent_protocol import terms_differences
from personal_agent_protocol.ui import PapConfirm, PapSessionShown

display = PapConfirm(
    company="shop.example",
    summary=operation.summary,                  # the company's words, verbatim
    terms=operation.terms or {},
    operation_ref=operation.operation_id,
    revision=operation.revision,
    expires_at=operation.expires_at,
    differences=list(terms_differences(operation)),
    does="buy",                                 # what it does, as the application's Rules class it
    session=PapSessionShown.of(session_key, signed_in=True),
)
meta = display.tool_meta()   # an MCP result's `_meta`: the page draws the card
said = display.text()        # what a page without a renderer, a transcript and a model read
```

- `text()` is *shop.example asks you to approve: … (revision …, until …)*, and
  *The terms changed since you saw them.* after it when `was` names the revision
  a newer one replaced. Links, images and HTML in the summary show as text
  (`inert_summary`): a page shows `summary` as text too, with at most emphasis,
  paragraphs and lists.
- The Session is a one-way reference (`PapSessionShown.of`: 12 hex digits of
  the SHA-256 of its Session Key), never the key or a token, and only the page sees even
  that: `model_view()` tells a model the company's words, the terms, what it
  does, the revision and whether the person is signed in there.
- The buttons are the host's own. Approving still goes through the host's
  approval surface, never because a model saw the display.

On the page, the TypeScript SDK types the same display and checks it:

```typescript
import { isPapConfirm } from "@datalayer/personal-agent-protocol";

const display = result._meta["reactor.ui/display"];
const asked = isPapConfirm(display) ? display.data : null; // PapConfirmData, or nothing to draw
```

`isPapConfirm` refuses another type or version, a missing or unknown field,
and a Session given by anything but its reference. Both SDKs are checked
against one committed example, `protocol/fixtures/pap-confirm-display.json`.

## Security boundary

- Conversation text never approves an operation, whoever wrote it.
- The model may explain an operation and what changed; the approval is the
  user's, in the host's interface, bound to one revision.
- A summary can't send the user elsewhere or load content while they decide:
  links, images and HTML show as text.
- An approval shows what the personal agent stated, not that the user saw the
  terms; a company that needs proof asks the user on its own website.
- Tokens stay host-only; errors carry codes only.
