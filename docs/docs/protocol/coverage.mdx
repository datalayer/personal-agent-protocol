# Protocol coverage

The SDKs target **Personal Agent Protocol draft 0.3, as of October 28, 2026**
(upstream commit `3e9bada`, reviewed October 30, 2026) and the Operations
extension version 2. The
upstream draft remains authoritative. This page records, requirement by
requirement, what the implementation and the conformance suite cover.

## Sources

The specification is published by the
[Personal Agent Protocol organization](https://github.com/personal-agent-protocol)
at [personalagentprotocol.org](https://personalagentprotocol.org), built from
[personal-agent-protocol/personal-agent-protocol](https://github.com/personal-agent-protocol/personal-agent-protocol).
Draft 0.3 is in progress there; version 0.2, which SDK 0.25 and 0.26
implement, is frozen at [/docs/0.2/spec](https://personalagentprotocol.org/docs/0.2/spec),
and version 0.1, which SDK 0.24 and earlier implement, at
[/docs/0.1/spec](https://personalagentprotocol.org/docs/0.1/spec). What changed
between them is in the upstream
[changelog](https://personalagentprotocol.org/docs/changelog) and, for the
SDKs, in [Migration](/releases/migration/#027--028).

The repository records the reviewed upstream revision in
`protocol/UPSTREAM.md` and maps individual normative requirements in
`protocol/requirements.yaml`.

The shared fixture corpus covers discovery (including the served host after
redirects, `major.minor` versions and issuers with a path), OAuth and MCP
protected resource metadata, client metadata, Session JWTs, delegations, token
responses, conversation event pages, feedback reports, and Operations objects. Both SDKs preserve unknown compatible fields and event types while
validating the required shape of known types.

## Required surface

| Area | Required behavior |
| --- | --- |
| Discovery | Fetch `/.well-known/poppy.json`; require the supported `major.minor` version (`0.3`), the final URL's path exactly `/.well-known/poppy.json` with no query, `organization.domain` equal to the host that served it after HTTPS redirects (case-insensitive), HTTPS for every URL, interfaces, issuer, and extensions; cache within safe bounds. |
| Company identity | Read the issuer from the domain's protected resource metadata (`resource` exactly `https://{domain}`; `auth.issuer` when several authorization servers are listed); fetch RFC 8414 metadata (path-aware for an issuer with a path) and bind the issuer, compared character for character, to a `protected_resources` entry `https://{domain}`; `grant_types_supported` with `refresh_token`; one issuer per company, the same `auth` on every domain naming it. |
| Personal-agent identity | Publish and verify HTTPS client metadata, same-domain JWKS and redirects, and `private_key_jwt` authentication; client assertions name the company's issuer in `aud`, are short-lived, and are signed with `ES256` or `PS384`, the last blindly if the agent chooses. |
| User identity | Maintain one stable, opaque, non-personal ID per user and company issuer (a pairwise subject identifier the agent assigns); optional Agent IDs under the same rules. |
| Sessions | A Session is local: a random `sid`, no network call. Every request to a company's APIs, conversations and protocol endpoints carries `Poppy-Session`; a company keys Sessions by `client_id` and `sid`; `invalid_session` starts one new Session, then stops. |
| Delegated keys | One delegated P-256 key per User ID signs each request's `poppy-session+jwt`; a `pap-delegation+jwt` of at most 24 hours in `pap_dlg` vouches for it and names no User or Company; the company verifies in the spec's four steps, and may cache a verified delegation. A jwks key never signs a Session JWT. |
| Sign-in | Direct authorization code with PKCE, loopback redirect URIs; device authorization (the link only on the issuer host or a host of its `protected_resources`, with the company's name and domain); and the Mediated Sign-In extension, an OAuth extension grant (`code_required`, `invalid_grant`, `expired_token`, `access_denied`, `invalid_scope`, credentials chosen by issuer). Sign-in doesn't know the Session and returns a refresh token. |
| Account access | Store rotating refresh tokens as secrets; get access tokens from them at the token endpoint, narrowed by scope or for one `resource`; sign out by revoking every refresh token held for the account. Access tokens are Bearer tokens: the SDKs send no DPoP proofs yet, and refuse a `DPoP` token type. |
| APIs | The Session header and an access token at OpenAPI and MCP; a 401 challenge with `scope` when signed out, `insufficient_scope` with the needed `scope`; a token for a service whose protected resource metadata names its own `resource`; for MCP, a token requested with `resource` = the server's `url`, valid only there; no redirect followed outside discovery. |
| Web | Join the agent's own browser to the Session through the company's form: a one-time code tied to that browser by a `__Host-` `SameSite=Strict` cookie, authorized by the agent at `{browser_session_endpoint}/authorize` with the Session header. |
| Conversations | Create, retry idempotently, read cursor events (`cursor`, `wait` as query parameters; `conversation_id` and `events` on every read), poll or stream (`Last-Event-ID` wins), identify speakers (`role` set by the company, `author` with its `type` and, for a company's person or persona, `id`, `name`, `image`), hand off and close idempotently, sign in, stay open after sign-out. |
| Extensions | Negotiate named major versions while ignoring unsupported extensions and unknown fields. |
| Excluded tasks and feedback | Read the tasks a company doesn't offer (`excluded_tasks`, each with an optional alternative); report a missing task (`task`, `description`) with the Session header; the company answers 202, or 200 with an alternative when the task can be done after all. |
| Operations v2 | Refuse an action with 403 `approval_required` and its operation, ask the user about every operation, retry the same request with its approval, perform at most once, across interfaces, with 503 and `Retry-After` while performing. |

## Coverage expectations

The overview's principles—existing standards, user control, privacy,
progressive adoption, and extensibility—must appear in defaults, APIs,
examples, and Studio copy. Security guidance becomes automated tests wherever
possible: secret redaction, safe metadata fetches, key and token custody,
fresh Session JWTs, retries, rate limits, sign-in preferences, consent presentation,
and safe errors.

Operations is implemented as an optional Reactor-backed PAP extension: the
client in Python and TypeScript, the company side in both reference
companies. Its conformance suite covers exact revisions, ownership, expiry, a
retry before and after the outcome, and a new revision on changed terms,
regardless of the channel where an operation was refused.

## Deliberate boundaries

Draft 0.3 does not define payments, push notifications, or message
attachments. The SDKs preserve unknown extension data but do not invent wire
formats for those areas. Company registration policy is also outside the
protocol; implementations may expose allow/block policy without presenting it
as a standard registration flow.

PAP complements rather than replaces MCP, OpenAPI, or peer-oriented agent
protocols. PAP scopes express what the company permits. Host application rules
express what the user permits. An action proceeds only when both allow it.
