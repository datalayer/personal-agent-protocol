# Protocol coverage

The SDKs target **Personal Agent Protocol draft 0.2, as of October 18, 2026**
(upstream commit `39b35bd`, reviewed October 22, 2026) and the Operations
extension version 1. The
upstream draft remains authoritative. This page records, requirement by
requirement, what the implementation and the conformance suite cover.

## Sources

The specification is published by the
[Personal Agent Protocol organization](https://github.com/personal-agent-protocol)
at [personalagentprotocol.org](https://personalagentprotocol.org), built from
[personal-agent-protocol/personal-agent-protocol](https://github.com/personal-agent-protocol/personal-agent-protocol).
Draft 0.2 is in progress there; version 0.1, which SDK 0.24 and earlier
implement, is frozen at [/docs/0.1/spec](https://personalagentprotocol.org/docs/0.1/spec).
What changed between them is in the upstream
[changelog](https://personalagentprotocol.org/docs/changelog#v0-2) and, for the
SDKs, in [Migration](/releases/migration/#024--025).

- [Overview and principles](https://personalagentprotocol.org/docs/introduction)
- [Draft specification](https://personalagentprotocol.org/docs/0.2/spec)
- [Implementation guides](https://personalagentprotocol.org/docs/0.2/guides)
- [Extensions](https://personalagentprotocol.org/docs/0.2/extensions)
- [Operations version 1](https://personalagentprotocol.org/docs/0.2/extensions/operations)
- [Open topics](https://personalagentprotocol.org/docs/path-to-1#open-topics)

The repository records the reviewed upstream revision in
`protocol/UPSTREAM.md` and maps individual normative requirements in
`protocol/requirements.yaml`.

The shared fixture corpus covers discovery (including the served host after
redirects, `major.minor` versions and issuers with a path), OAuth and MCP
protected resource metadata, client metadata, session-token responses,
conversation event pages, feedback reports, and Operations objects. Both SDKs preserve unknown compatible fields and event types while
validating the required shape of known types.

## Required surface

| Area | Required behavior |
| --- | --- |
| Discovery | Fetch `/.well-known/poppy.json`; require the supported `major.minor` version (`0.2`), `organization.domain` equal to the host that served it after HTTPS redirects (case-insensitive), HTTPS for every URL, interfaces, issuer, and extensions; cache within safe bounds. |
| Company identity | Fetch RFC 8414 metadata (path-aware for an issuer with a path) and bind the issuer, compared character for character, to a `poppy_domains` entry; one issuer per company, the same `auth` on every domain naming it. |
| Personal-agent identity | Publish and verify HTTPS client metadata, same-domain JWKS and redirects, and `private_key_jwt` authentication; client and Session assertions name the company's `auth.issuer` in `aud`, live at most five minutes, and a `jti` is refused again per `client_id`. |
| User identity | Maintain one stable, opaque, non-personal ID per user and company issuer. |
| Sessions | Start signed out, renew by session ID, preserve parallel sessions, and treat session tokens as opaque. |
| Proof of possession | A DPoP key pair per User ID; sign ES256 (or a listed algorithm); a new proof per request; nonces; RFC 9449 §4.3 checks at the company, replay refused at the token endpoint; 400 OAuth errors at the token endpoint, 401 challenges elsewhere. |
| Sign-in | Direct authorization code with PKCE, device authorization (link only on the issuer host or `poppy_domains`, with the company's name and domain), and mediated sign-in (HTTP 200 statuses, `invalid_scope` / `account_mismatch` / `sign_in_not_found`, credentials chosen by issuer and discarded after); a Session stays tied to the account it was ever signed in to. |
| Account access | Store rotating account tokens as secrets; exchange them only at the token endpoint; narrow scopes/resources and revoke on sign-out. |
| APIs | DPoP for OpenAPI; for MCP, a token requested with `resource` = the server's URL: DPoP when its protected resource metadata lists `dpop_signing_alg_values_supported`, Bearer otherwise, valid only at that exact URL; no redirect followed outside discovery. |
| Web | Join an isolated browser context to the session with a short-lived assertion and a validated return location. |
| Conversations | Create, retry idempotently, read cursor events (`cursor`, `wait` as query parameters; `conversation_id` and `events` on every read), poll or stream (`Last-Event-ID` wins), identify speakers (`role` set by the company), hand off and close idempotently, sign in, stay open after sign-out. |
| Extensions | Negotiate named major versions while ignoring unsupported extensions and unknown fields. |
| Feedback | Report a task the company offers no way to do (`kind` `missing`, `task`, `description`) with a Session Token; the company answers 202. |
| Operations v1 | Propose immutable revisions, obtain exact approval, confirm at most once, track, recover, and cancel across channels; an account's operation only from a Session signed in to that account (`sign_in_required` otherwise). |

## Coverage expectations

The overview's principles—existing standards, user control, privacy,
progressive adoption, and extensibility—must appear in defaults, APIs,
examples, and Studio copy. Security guidance becomes automated tests wherever
possible: secret redaction, safe metadata fetches, key and token custody,
fresh proofs, retries, rate limits, sign-in preferences, consent presentation,
and safe errors.

Operations is implemented as an optional Reactor-backed PAP extension: the
client in Python and TypeScript, the company side in both reference
companies. Its conformance suite must cover exact revisions, ownership, expiry,
idempotent confirmation, recovery, and cancellation regardless of the channel
where an operation was proposed.

## Deliberate boundaries

Draft 0.2 does not define payments, push notifications, or message
attachments. The SDKs preserve unknown extension data but do not invent wire
formats for those areas. Company registration policy is also outside the
protocol; implementations may expose allow/block policy without presenting it
as a standard registration flow.

PAP complements rather than replaces MCP, OpenAPI, or peer-oriented agent
protocols. PAP scopes express what the company permits. Host application rules
express what the user permits. An action proceeds only when both allow it.
