# Open topics and SDK gaps

PAP draft 0.3 is intentionally incomplete. Its
[upstream open-topics page](https://personalagentprotocol.org/docs/path-to-1#open-topics)
currently leaves three areas unspecified:

- **Payments:** how a personal agent pays through PAP or composes PAP with an
  existing payment protocol.
- **Push notifications:** how a company reaches a personal agent when no
  request or event stream is open.
- **Attachments:** how messages carry receipts, labels, images, or interactive
  forms beyond the existing text and structured-data fields.

These are protocol omissions, not SDK backlog items. The Python and TypeScript
packages do not invent core wire fields, security semantics, or conformance
claims for them. An experiment must use an explicitly negotiated extension,
prefer a domain-qualified extension name, and document that it is outside PAP
draft 0.3. Applications must continue to work when the other party ignores an
unknown extension.

## SDK implementation gaps

An SDK gap is different: draft 0.3 or Operations v2 already defines the
behavior, and this repository doesn't implement it yet or leaves it to the host.
Current examples include:

- DPoP, a SHOULD for personal agents: the SDKs send no DPoP proofs yet and refuse
  a `DPoP` token type;
- helpers the Guides suggest: choosing among the sign-in methods, matching a
  task's scopes to a held refresh token, and revoking the previous refresh token
  after a wider sign-in;
- rate limits and `RateLimit` headers in the reference companies; and
- in Node, socket pinning for metadata fetches.

The [implementation status](./status) and
[requirements ledger](https://github.com/datalayer/personal-agent-protocol/blob/main/protocol/requirements.yaml)
track these gaps. A model or parser marked implemented does not imply that its
network flow, durable state, authorization checks, or conformance suite also
exists.

## Datalayer integrations

Datalayer Studio and backend work is downstream product integration. Appspec
roles, Canvas controls, IAM services, KMS-backed publication, deployment
gateways, Rules, and observability can implement or operate PAP, but they are
not part of the PAP standard and must not be presented as conformance
requirements.

## Change policy

The upstream page says the list is not exhaustive and the entire protocol is
still a draft. Before adding a new public SDK abstraction, check the current
specification, extensions, guides, and open topics. Record the exact upstream
revision in the requirement ledger. If upstream later standardizes an
experimental extension, migrate deliberately rather than silently treating
the old shape as compliant.
