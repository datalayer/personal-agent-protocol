# Migration

What to change when you upgrade across a release that breaks the API. The SDKs
keep no compatibility shims: an old shape is refused, not translated. Each
section names the release that introduced the change; the
[changelog](https://github.com/datalayer/personal-agent-protocol/blob/main/CHANGELOG.md)
has the full list.

## 0.34 → 0.35

0.35.0 breaks nothing: both SDKs and both reference companies still announce and accept
0.4 as published, and nothing changes until you ask for the 1.0 draft.

| Addition | What to do |
| --- | --- |
| The 1.0 draft, opt-in (spec 3.1, 3.4) | Nothing, to stay on 0.4. To use companies that serve the draft, give the discovery client the versions your agent implements: `DiscoveryClient(protocol_versions=("0.4", "1.0"))` (`discoverCompany(domain, { protocolVersions: ["0.4", "1.0"] })`), and start Sessions with `company=` (or `protocol_version=`). A company serves it with `CompanyConfig(protocol_versions=("0.4", "1.0"))` (`protocolVersions`). `AVAILABLE_PROTOCOL_VERSIONS` lists what the SDK implements, `SUPPORTED_PROTOCOL_VERSIONS` stays the default (`0.4`) |
| A document's version | `DiscoveryDocument` (`parseDiscoveryDocument`) now accepts any version the SDK implements, `1.0` included; which one an agent uses is decided at discovery. `DiscoveryDocument.chosen_version` answers for the default versions, `choose_version(implemented)` (`chosenVersion(document, implemented)`) for others |
| Lookalike domains (spec 10.3) | Show the domain with a company's name: `Organization.label` (`organizationLabel`). Give `PapConfirm` and `PapReplies` the domain or the label as `company`, never the name alone. The `pap` CLI's protected prompts now name the domain too |
| Conformance | `ConformanceContext(protocol_versions=...)` runs the suite at the draft; the fixture `protocol.major-version-unsupported` now uses `2.0` |

## 0.33 → 0.34

0.34.0 breaks nothing: it adds what 0.33.0 left out of version 0.4 as published, in both
SDKs and both reference companies.

| Addition | What to do |
| --- | --- |
| Operations on websites (Operations 2, 4, 6, 7) | A host that joins a browser to a Session may now declare `operations` on it. When a response its own browser received carries `Poppy-Operation`, take it with `WebsiteOperations.reference(headers, joined=browser_sessions.joined_sessions(endpoint))` (`WebsiteOperations.reference(headers, { joined })`): only a Session you joined that browser to counts. Then `operation(...)`, approve as at an API (`ask_user` or `approve_as_agent`), `record(...)` (through `OperationsClient.send`), and have the browser make the request again. If that request fails or answers a new reference, call `before_approving_again(earlier, ...)` first: `wait`, `performed` (never approve again) or `approve` |
| A company's website (`pap.company.website`) | Contribute a `CompanyWebsite` whose `handle(WebCall)` returns a `WebResult`; an action that needs approval returns `WebResult(operation=ProposedOperation(...), own_approval=...)`. With `website_operations=True` (and `web`), the company lists the operations `endpoint`, answers a joined browser that declared Operations 3 with `403` and `Poppy-Operation`, serves `POST /poppy/operations`, and performs the action on the browser's next request once the approval is recorded; any other browser gets `own_approval` |
| Browser Control, version 1 | Optional. A host whose browser leaves marked steps to the User, hands it control and runs `controller_script(organization_domain, channel)` declares `browser-control` with `negotiate_extensions(..., supported={**SUPPORTED_EXTENSIONS, "browser-control": "1"})`; before each browser action of the model, `BrowserControl.check_change` / `check_submit` with `page_marks(html)`. A company lists it with `browser_control=True` and marks its pages with `data-poppy-user-step` |
| `BrowserSessionStart.sid` | The join's result names the Session; `BrowserSessionClient.joined_sessions(endpoint)` lists the Sessions a client joined its browser to |
| Stored records | A company's `StoredOperation` gains `website` (written only when true) and `WebSession` `extensions`; records written by 0.33 read as before |

The ledger: `OPS-2-02`, `OPS-4-01`, `OPS-6-13`, `OPS-6-14` are implemented and `OPS-5-09`
is no longer partial; the Browser Control extension's rows are added (`BC-4-01` to
`BC-6-01`). The conformance suite adds `operations.website-reference`.

## 0.32 → 0.33

0.33.0 moves both SDKs and both reference companies from draft 0.4 as of `46beb21` to
**version 0.4 as published** (upstream `4803900`, 2026-11-10, the 1.0 release candidate;
the specification is frozen at `/docs/0.4/spec`). Seven changes are breaking, with no
compatibility: an agent at 0.32 finds no excluded tasks, skills or feedback endpoint at a
company at 0.33, and neither side understands the other's operations. Both still say
`Poppy-Version: 0.4`, so move every role at once. Python spells the names below in
`snake_case`, TypeScript in `camelCase`.

| Change | What to do |
| --- | --- |
| `PROTOCOL_REVISION` | `2026-11-10`; `PROTOCOL_PROFILE` stays `0.4`, and `protocol_version` `1.0` (the draft at `/docs/spec`) is neither announced nor accepted |
| Task coverage per Session (spec 3.1, 9) | Read nothing of it from `poppy.json`: `tasks = await TasksClient(transport=transport).get(company, session=session)` (`new TasksClient({ transport }).get(company, { session })`) before starting on a task, then `tasks.excluded_tasks`, `tasks.skills`, `tasks.feedback_endpoint`. One call per Session: the response is never reused in another. Gone: `DiscoveryClient.excluded_tasks`, `feedback_endpoint(document)` / `feedbackEndpoint`, `DiscoveredCompany.skills`, `DiscoveryDocument.usable_skills`, `ExcludedTasks`. A company on the SDK serves `GET /poppy/tasks` and lists `tasks.endpoint` by itself; one that publishes its own `poppy.json` replaces `feedback`, `excluded_tasks` and `skill_index` with `tasks.endpoint` and serves the response there |
| Operations version 3 (Operations 2, 5, 6) | `OPERATIONS_VERSION` is `"3"` and version 2 is gone on both sides. Build every approval with its approver: `ask_user(...)` / `askUser` returns `approver: "user"`; `Approval(operation_id=, revision=, approver="user")` when you build one by hand. A `Poppy-Approval` or `_meta` approval without `approver` approves nothing |
| Agent approvals (Operations 5) | To approve on something the user told the agent: `await client.approve_as_agent(operation, instruction=AgentInstruction(text=..., covers=check))` (`approveAsAgent(operation, { instruction: agentInstruction(text, covers) })`). `covers` is your own check of the terms and only `True` approves; `OperationError` `ask_user` means ask the person with `ask_user`. Keep your own record under `reference=client.new_reference()` |
| Operations require terms (Operations 3) | `Operation.terms` is always there and `summary` may be absent: show `operation.shown` (`operationShown(operation)`). A company's `ProposedOperation(action=, terms=, summary=None)` needs `terms`; `CompanyService.revise(operation_id, terms=, summary=)` |
| Declining an approval (Operations 6) | After sending an approval read `sent.status == "declined"` (`sent.declined.reason`, `.alternative`): tell the user, never send it again, and ask them before approving a new revision of that action. By hand: `ApiResponse.declined`, `McpToolResult.declined`, `Message.declined` (`messageDeclined(message)`). A company declines with `CompanyConfig(decline=lambda request: Decline(reason=...) or None)` |
| `extension_required` in a JSON body at APIs (spec 3.3, 7) | Nothing for a caller of `ApiClient`; `extension_required(status, payload)` / `extensionRequired` no longer takes the challenge. A company's own API answers 403 with `{"error": "extension_required", "extension": ...}` and no `WWW-Authenticate` |
| Sessions found by User ID too (spec 5.3) | A company: `end_session(client_id, sid, pairwise_user_id)` / `endSession(clientId, sid, pairwiseUserId)`; a Session record written at 0.32 is not found again, and its Session starts anew, signed out. A request naming a known `sid` with another User ID is no longer `invalid_session` |
| Device Sign-In links (spec 4.3) | `DeviceSignInClient.begin(...)` no longer takes `protected_resources` / `protectedResources`; `verification_host_allowed(url, issuer=, domain=)`. A company's `device_page` is on its own domain |
| Sign-ins someone else started (spec 4.2, 10.8) | Optional and recommended: `DirectSignInClient.begin(..., cross_device=True)` when the link opens on another device (the request then lives at most 300 seconds), and `complete(callback, completed_by=tenant_id)` when you know which of your users is in the browser at the redirect. A hosted consent or device page shows `heading` and `caution` from `authorization_request()` / `device_request()` |
| The Session header on fetched pages (spec 5.2) | Optional (a SHOULD): fetch a company's pages with `PageClient(transport=transport).fetch(url, session=session, company=company)`. A company's own pages call `CompanyService.page_session(request)` |
| Scopes (spec 3.2, 4.7) | `DiscoveredCompany.scopes_supported` / `scopesSupported(company)` in place of the issuer's list alone |
| `PapConfirm` | Display version 3: `terms` required, `summary` optional, and `approved_by`, `instruction`, `declined` |

Not in 0.33: operations on websites (the `Poppy-Operation` header and the extension's
`endpoint`) and the Browser Control extension (both in 0.34). A host on 0.33 that joins a
browser to a Session passes `extensions` without `operations` for that Session.

The ledger (`protocol/requirements.yaml`) is at `4803900`. Withdrawn: `PAP-9.1-01` (the
excluded tasks document), `OPS-5-04` and `OPS-5-05` (version 3 lets the agent approve on
the user's instruction). Added: `PAP-4.2-20`, `PAP-4.2-21`, `PAP-5.2-19`, `PAP-5.2-20`,
`PAP-9-01` to `-03`, `OPS-2-02`, `OPS-4-01`, `OPS-5-07` to `-09`, `OPS-6-07` to `-14`, and
guide entries; `OPS-2-02`, `OPS-4-01`, `OPS-6-13` and `OPS-6-14` are open (operations on
websites). Rewritten: `PAP-3-08`, `PAP-3.2-22`, `PAP-4.3-02`, `PAP-5.2-18`, `PAP-5.3-02`,
`PAP-9.4-01`, `-03`, `-05`, `OPS-2-01`, `OPS-3-01`, `OPS-5-02`, `OPS-5-06`, `OPS-6-04` to
`-06`, `OPS-7-04`. Conformance cases renamed: `security.session-sub-stays-the-same` to
`security.session-found-by-user-id`, `protocol.feedback-endpoint-https` and `-listed` to
`protocol.tasks-endpoint-https` and `-listed`; new: `protocol.tasks-per-session`,
`protocol.operations-version-2-not-used`, `protocol.extension-required-not-in-a-challenge`,
`protocol.operation-requires-terms`, `operations.agent-approval`,
`operations.approval-without-approver`, `operations.approval-declined`. The vendored
schemas are replaced whole at `ed47408`.

## 0.31 → 0.32

0.32.0 moves both SDKs and both reference companies from version 0.3 as published to
**draft 0.4 as of upstream `46beb21`** (2026-11-06; served at `/docs/spec` until it is
published). There is no compatibility with 0.3: every request with the Session header
names its version in `Poppy-Version`, so an SDK or company at 0.31 and one at 0.32
refuse each other (`version_unsupported`). Python spells the names below in
`snake_case`, TypeScript in `camelCase`.

| Change | What to do |
| --- | --- |
| `PROTOCOL_PROFILE` and `PROTOCOL_REVISION` | `0.4` and `2026-11-06`; fixtures and documents say `"protocol_version": "0.4"` |
| Direct Sign-In is preferred (spec 4) | `DiscoveredCompany.preferred_sign_in` / `preferredSignIn(company)` and `sign_in_types` / `signInTypes`: use Direct Sign-In when the company offers it; the conformance runner does |
| Several protocol versions (spec 3.4) | `DiscoveryDocument.supported_versions`; `discover` chooses the newest compatible version (`choose_protocol_version`, `chooseProtocolVersion`) and fetches its document; `PapSession.protocol_version` is sent in `Poppy-Version`; `version_unsupported` (`version_unsupported(response)`, `versionUnsupported`) means discover again and start a new Session. A company sets `CompanyConfig.protocol_versions` and `deprecated_versions` (`Deprecation` and `Sunset` headers) |
| Extensions are per-version lists, declared per request (spec 3.3, 3.4) | `poppy.json`'s `extensions` maps each name to a list of `{version, ...}` entries (`document.extension(name, version)`, `companyExtension`); client metadata no longer lists extensions (`ClientMetadata.extensions` is gone, `AgentIdentity.supported_extensions` says what the agent implements); start a Session with `extensions=negotiate_extensions(...)` or `company=`, and they go in `Poppy-Extensions` (`format_extensions_header`, `parse_extensions_header`) |
| Conversations across versions (spec 8.2) | A conversation records the versions it started in; `CompanyConfig.conversation_carry_over=False` refuses a message, handoff or cancel from other versions with `version_mismatch` (409), its `protocol_version` in the error's details |
| A conversation's state in four fields (spec 8.6, 8.7) | `status` is gone: read `working`, `handoff`, `responder` and `closed` (`ConversationEventPage.state`, `conversationState`); a stream's `working` event (`WorkingChanged`); `read_until_done` / `readUntilDone` reads until `working` is false |
| Requests accepted, then acted on (spec 8.3, 8.9, 8.12) | Every conversation POST carries a top-level `id`: `request_id` / `requestId`, defaulting to the message's `id`, which no longer goes in the message; `generate_request_id` / `generateRequestId` replace `generate_message_id`; a receipt without `wait` holds only `conversation_id`; `message_id_conflict` is now `request_id_conflict`; `cancel_handoff` / `cancelHandoff` (`POST {id}/handoff/cancel`); a close is accepted with 202. Company stores: the `message_id` record kind is now `request_id` (`RequestReceipt`) |
| What a message took into account (spec 8.4) | `Message.as_of_request` on a company agent's message, `as_of_cursor` on one the agent wrote (`send(as_of_cursor=...)`, `asOfCursor`); `PapReplies` is version 5 |
| The browser join scope and website flags (spec 3.1, 4.7, 6) | A signed-in join needs `poppy:browser-sign-in` (`BROWSER_SIGN_IN_SCOPE`): request it with the task's scopes, else `BrowserSessionError` `insufficient_scope`; `web.unscoped` and `web.disabled` (`browser_sign_in_unscoped`, `browsing_disabled`); a company sets `web_unscoped` / `web_disabled` |
| A DPoP key per User ID (spec 4.5) | `DpopKeyCustody.key_for` / `forget` (`keyFor`) take `sub`; a sign-in or refresh at an issuer that lists ES256 names its User ID: `pairwise_user_id=` / `pairwiseUserId` on `DeviceSignInClient.begin`, `DirectSignInClient.begin`, `MediatedSignInClient.sign_in` and `RefreshTokenContext`, refused before any request without one. A CLI key file's DPoP keys are made again |
| Sign-in's other changes (spec 3.2, 4.5, 4.7, 5.2) | Resource metadata whose `resource` isn't the URL it was derived from is treated as absent; `document.scope_descriptions(openapi)` / `scopeDescriptions` lets `auth.scopes` win; a company with `auth.disabled` that never issued a refresh token answers refresh and revocation unverified; the reference companies refuse a delegated key that signed for another User ID (`invalid_session`, a new `delegated_key` record kind) |
| Operations (Operations 3, 5, 6) | `Approval.approved_at` and `input_type` (`ask_user(input_type=...)`, `inputType`), in `Poppy-Approval` and `_meta`; any Session of the same agent and User approves, an operation returned signed out only while signed out; a revision is the terms (else the `summary`) and `expires_at`; the approving request is compared by meaning |
| The guides | `CompanyService.revoke_client` / `revokeClient`; `CompanyConfig.refresh_reuse_revokes` / `refreshReuseRevokes` (off by default) |
| The UCP extension, version 1 (new) | `fetch_ucp_profile(http, company)` / `fetchUcpProfile(company)`, `UcpClient`, `speaks_ucp` / `speaksUcp`; a company sets `CompanyConfig.ucp` and `ucp_products` (`ucpProducts`). The issuer's metadata now lists `token_endpoint_auth_methods_supported: ["private_key_jwt"]` |

The ledger (`protocol/requirements.yaml`) is at `46beb21`. Withdrawn: `PAP-8.7-01` (the
conversation `status` it described is gone); `PAP-3.4-06` and `PAP-3.4-10` are not used:
those statements are MAY or descriptive. Added: `PAP-3.4-01` to `-05`, `-07` to `-09`,
`PAP-4-01`, `PAP-4-02`, `PAP-4.5-02`, `PAP-6-16` to `-19`, `PAP-8.3-02`, `PAP-8.4-04`,
`PAP-8.4-05`, `PAP-8.9-01`, `PAP-8.12-01`, `OPS-6-04` to `-06`, and guide entries.
Rewritten for 0.4: `OPS-2-01`, `PAP-3.1-01`, `PAP-3.3-02` to `-05`, `PAP-8.3-01`,
`PAP-8.4-03`, `PAP-8.5-03`. The conformance case `conversations.message-id-conflict` is
now `conversations.request-id-conflict`; new cases cover Direct Sign-In, supported
versions, `Poppy-Version`, `Poppy-Extensions`, the browser scope and website flags,
`handoff/cancel` and `as_of_request`. The vendored schemas are replaced whole at
`46beb21`.

## 0.30 → 0.31

0.31.0 moves both SDKs and both reference companies from draft 0.3 as of `ec16efa` to
**version 0.3 as published** (upstream `2289293`, 2026-11-04; the specification is
frozen at `/docs/0.3/spec`). Three changes are breaking on the wire, with no
compatibility: an SDK or company at 0.30 and one at 0.31 refuse each other's
Session JWTs. Python spells the names below in `snake_case`, TypeScript in
`camelCase`.

| Change | What to do |
| --- | --- |
| Delegations are typed `poppy-delegation+jwt` and travel in the `poppy_dlg` header (spec 5.2); `pap-delegation+jwt` and `pap_dlg` are refused | Nothing in code: both SDKs and companies send and check the new names. Upgrade agent and company together |
| A Session the Company ended answers `session_ended` (400, JSON body; spec 5.3, 5.5); `invalid_session` means only a failing header or a refused `client_id` | `SessionHttpClient` / `SessionFetchClient` and the MCP clients start a new Session once on `session_ended` and send the request again; `invalid_session` reaches the caller as it is. A company built on the reference service answers the new code itself |
| A message's extension content is in `extensions`, keyed by the extension's name; Operations' `operation` and `approval` are under `extensions.operations` (spec 8.4, Operations 2, 4, 6); a message needs `text`, `data`, `context` or `extensions` | Read `message.operation` / `messageOperation(message)` and `message.approval` / `messageApproval(message)`; build an approving message with `operations_content(approval=...)` / `operationsContent({ approval })`. A company agent's `Reply.operation` is placed by the service |
| The Links and Disclosures extensions, version 1 | A Company lists them with `CompanyConfig.links` and `.disclosures` and gives a reply `links=` / `disclosures=`; they go only to an agent that lists the same version, the notice in `text` otherwise. The agent reads `message.links` / `messageLinks(message)` and `message.disclosures` / `messageDisclosures(message)`; `pap.ui`'s replies display is version 4 and carries them |
| A Company may grant fewer scopes than requested and rejects only missing or unknown ones with `invalid_scope` (spec 4.7) | Read the token response's `scope`, as before. `CompanyConfig.agent_scopes` (`agentScopes`) grants fewer. When a task needs more access, `scopes_to_request(held, needed)` / `scopesToRequest` names every scope the new sign-in asks for |
| `auth.disabled` and `unauthorized_client` (spec 3.1, 3.2, 4.1) | `DiscoveryDocument.sign_in_disabled` / `signInDisabled(document)`: the SDKs start no sign-in with such a Company and `require_oauth` raises `sign_in_disabled`. `CompanyConfig.sign_in_disabled` publishes it; a client policy's `allows_sign_in(client_id, grant_type)` / `allowsSignIn` answers `unauthorized_client` from the grant's endpoint |
| Company-first Direct Conversations (spec 8.10) | `ConversationClient.accept_user_request(endpoint, parent_id, event_id)` / `acceptUserRequest` accepts a `user_requested` event: both IDs, no message, the company speaking first; sent again, the same conversation comes back, even once closed. | The delegation `iat` check is gone (spec 5.2); the Operations checks answer as the first failing one in the listed order (Operations 6) | Nothing: a Session JWT whose `iat` is past its delegation's `exp` but inside the window is accepted; the reference companies already checked in the listed order |
| Idempotency records are scoped to the agent, the User and any account, not the Session (guides) | A retry in a new Session matches; a company store sees the same record kind with a different key |
| `organization.logo_uri` and `skill_index` (spec 3.1, 9.4) | `Organization.logo_uri`, shown next to the name and domain (`DeviceSignInStart.organization_logo` / `organizationLogo`); `company.skills` / `companySkills(company)` and `DiscoveryClient.fetch_skill(entry)` / `fetchSkill(entry)`, the digest verified. `CompanyConfig.logo_uri` and `.skills` publish them |
| A conversation endpoint at another provider (spec 4.5) | `ServiceTokens.token_for(endpoint)` / `tokenFor` already asks for a token by `resource` when the endpoint's metadata names one; `CompanyConfig.conversation_resource` (`conversationResource`) plays such a provider |
| Explicit replies (guides) | No wire change: the demo company agents answer a bare "yes" or "done" with a question (`acknowledgement_only`, `WHICH_ONE`); the Operations example's agent is instructed the same way |
| `PROTOCOL_REVISION` | `2026-11-04` |

Not implemented: the UCP extension, version 1 (`extensions.ucp`), a decision for the
host. The conformance case `conversations.direct-of-direct-refused` now expects
`invalid_request`. The ledger (`protocol/requirements.yaml`) is at `2289293`: `OPS-6-04`
and `OPS-6-05` are withdrawn, and `PAP-3.2-34` to `-36`, `PAP-5.2-18`, `PAP-8.4-03`,

## 0.28 → 0.29

0.29.0 implements DPoP (spec 4.5, RFC 9449) in both SDKs and both reference
companies, and moves the target from upstream `3e9bada` to `ec16efa` (revision
2026-10-30), still draft 0.3, with no compatibility with the earlier text. A company
that lists no DPoP algorithm sees the same requests as from 0.28. Python spells the
names below in `snake_case`, TypeScript in `camelCase`.

| Change | What to do |
| --- | --- |
| A token request names its tenant and what the issuer lists | `SessionClient.token_request(..., tenant_id=, dpop_signing_algs=)`: both required, `dpop_signing_algs` `None` when the metadata lists nothing |
| Each sign-in and refresh passes `dpop_signing_alg_values_supported` on, or sends no proof | `DeviceSignInClient.begin(..., dpop_signing_algs=)`, `DirectSignInClient.begin(..., dpop_signing_algs=)`, `RefreshTokenContext.dpop_signing_algs`, from `metadata.dpop_signing_alg_values_supported` |
| Mediated Sign-In names its tenant, whose DPoP key proves | `MediatedSignInClient.sign_in(..., tenant_id=)` is required; it reads the algorithms from `company` |
| An access token is `Bearer` or `DPoP` | `TokenResponse.token_type` and `AccessToken.token_type` are one of the two; a host that keeps a token keeps its type, and a `DPoP` token sent by hand needs a proof: use `session_headers` |
| A `DPoP` token type is refused only when no proof went | `unsupported_token_type` no longer means every `DPoP` answer |
| A new contribution point, `pap.dpopProver` | Nothing, for one process: the default keeps one key per company for a tenant in memory. A host whose tokens outlive a process contributes `JoseDpopProver` with a durable `DpopKeyCustody` |
| Reference company: `dpop_binding`, off by default | `CompanyConfig.dpop_binding` (`off`, `optional`, `required`), `dpop_nonces`, `dpop_nonce_lifetime`, `dpop_proof_window`; turning it on lists ES256 and changes the `WWW-Authenticate` schemes (`token_schemes`) |

| `DiscoveryDocument.needs_issuer` means something else | It says the Company offers sign-in (`auth.issuer`, `access: signed_in`, Mediated Sign-In), not that it lists an interface.
