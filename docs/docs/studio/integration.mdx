# Datalayer Studio integration

:::info Planned product integration

This page defines the intended Studio experience. It is not implemented yet.

:::

Studio will support PAP in two explicit roles: consume an external company as
a personal agent, and publish a deployed application as a PAP company.

## Consume a company

1. Add a Personal Agent Protocol connection and enter a company domain.
1. Studio verifies discovery and shows sign-in modes, scopes, APIs, company
   agent, web support, and extensions.
1. The maker selects the least authority needed and maps capabilities to
   Studio rules.
1. Preview starts signed out and asks the person to sign in only when needed.
1. A task can continue through an API, conversation, or isolated browser while
   Activity records transitions without exposing credentials.
1. Consequential work is shown as one revisioned operation that the person
   explicitly approves or declines before the request is sent again.

## Publish a company

The Ship experience selects company-agent conversations, OpenAPI, MCP, browser
session joining, and optional Operations v2. It also configures guest access,
scopes, accepted personal agents, rate limits, and actions requiring exact
approval.

Each deployment receives a dedicated Datalayer subdomain first, with verified
custom domains later. The domain publishes `/.well-known/poppy.json`; a shared
path is insufficient because PAP binds discovery to the requested domain.

The company-agent adapter invokes the deployed LOOP application through its
normal runtime boundary. It does not reinterpret an A2A endpoint as PAP.

## Backend ownership

- IAM owns consent, direct/device authorization, encrypted refresh tokens,
  revocation, app principals, scope grants, and expiring authorization state
  with atomic consume semantics.
- KMS-backed signing owns the keys for client assertions and delegations, and
  published metadata/JWKS.
- Durable services own pairwise IDs, sessions, replay IDs, conversations,
  events, operation revisions/results, and idempotency records.
- The MCP gateway accepts only resource-bound PAP Bearer tokens.
- Deployment gateways serve discovery, authorization, conversation, browser,
  and API routes and enforce limits.
- A backend metadata gateway owns all outbound PAP document fetches. Its Node
  Reactor host installs `NodeUrlSafetyPolicy` from the SDK's server entry,
  rejects a hostname when any A or AAAA result is non-public, sends no ambient
  credentials, and applies the SDK's redirect and byte bounds. Production
  egress must additionally pin the connection to an approved address or
  enforce the resolved set at a proxy; DNS preflight alone does not close the
  rebinding interval.
- That gateway returns typed, verified summaries to Studio and runtime code:
  discovered company, exact issuer binding, or client metadata plus public
  JWKS. Raw response bodies and unverified URLs do not enter Appspec, model
  context, Canvas state, logs, or tool arguments.
- Cache keys include the tenant trust policy, document kind, and canonical
  URL. Client metadata never follows redirects. JWKS caches retain overlapping
  rotation keys only within bounded HTTP expiry; an unknown `kid` can trigger
  a rate-limited refresh, not an unbounded fetch loop.

Models and tools receive safe handles, never credentials. Signing, storage,
approval, rotation, and token attachment remain deterministic capabilities
outside the model loop.

Agent Runtimes depends on the SDK in Python and TypeScript and owns an
aligned `PapPersonalAgentCapability`. Its company-discovery and agent-identity
methods return top-level-frozen/read-only public summaries: organization, protocol version,
verified issuer, interface kinds, sign-in methods, extension versions, client
name, redirect count, and signing algorithms. Operational endpoint URLs, raw documents,
JWK coordinates, authorization material, assertions, Session JWTs, and tokens are
absent by construction and regression-tested in both languages. The didactic
examples perform metadata calls in process; a Datalayer deployment injects a
typed metadata gateway carrying opaque tenant/application context so DNS
pinning, caches, egress, rate limits, and audit remain server-owned. Direct
Sign-In stays a separate authorization gateway plus trusted Preview handoff
and is never exposed as an agent tool.

The Agent Runtimes examples still show the SDK's 0.27 shape, DPoP proofs among
it, until that package moves to 0.28. The split they make executable carries over:
a read-only Loop tool works with real signed material and returns only policy
evidence, a Reactor-contributed browser view never places a Session JWT, token,
identifier, or JWK in React state, and the authorization gateway alone imports
`./server` for signature and durable replay verification.

The paired Session lifecycle examples extend this into the authorization
gateway contract. Studio supplies only opaque tenant, user, and company
references; the gateway resolves the stable pairwise subject, signer, Session
signer, and token endpoint, then calls `SessionClient.start`. Credential
replacement stays inside the gateway. Canvas and
the model receive only lifecycle status, granted scope names, and an opaque
Session reference—not the pairwise subject, `sid`, assertions, Session JWTs, or
token response.

The Agent Runtimes `PAP Guided Journey` is the reference UX for explaining
this boundary in Studio. A single step index drives the user conversation,
company-visible state, and redacted protocol inspector, making transitions in
authority visible instead of reducing them to JSON. Studio onboarding and
connection diagnostics should reuse that three-perspective pattern: show what
the user experiences, what the company can know, and which host-owned exchange
advanced the workflow, without rendering live credentials.

The SDK now supplies safe discovery, client/JWKS retrieval, and Direct Sign-In
orchestration in Python and TypeScript, plus a DNS-aware Node policy. Datalayer
integration still owns the durable cache, connected-address
enforcement, tenant policy, rate limiting, audit summaries, availability
controls, browser surface, and authorization-state persistence. This split
keeps reusable PAP validation in the SDK while deployment-specific network and
user-interaction authority remains in the backend.

Generated Python and TypeScript API inventories now define the supported SDK
boundary and are checked for drift in documentation CI. Datalayer backend and
Studio packages should import only those public symbols. Node services import
network policy, `JoseSigner`, Session JWT verification, and replay-cache contracts
from the explicit `./server` subpath; browser and Canvas bundles stay on the
portable entry and receive no company signing or verification APIs. Package regression tests inspect the emitted
portable entry for these forbidden server symbols. This prevents product
integration from quietly depending on SDK internals or bundling company key
custody into Studio UI code.

For Datalayer, the entry split maps to a deployable ownership boundary:

- Canvas, Preview UI, and browser connection flows import only the portable
  entry and exchange opaque `company_ref` and `session_ref` handles;
- authorization gateways may use either SDK's `DirectSignInClient`; the
  TypeScript client stays in a trusted Node/desktop host even though its types
  are portable, because its Reactor resolves signing and protected state;
- the backend metadata and authorization gateways import `./server`, attach
  the DNS policy, and perform Session JWT verification against durable replay
  state;
- the KMS plugin implements the Reactor `Signer` contract so the private keys
  behind client assertions and delegations remain non-extractable and outside Node process
  memory; and
- IAM contributes `pap.pairwiseUserIdStore`, atomically keyed by application,
  Datalayer user, and exact verified issuer; runtimes receive only the random
  `usr_…` value and never derive it from profile data; and
- IAM contributes `pap.authorizationStateStore` with encrypted, bounded-TTL
  pending state and atomic `take`; keys are hashes of OAuth state, and the
  consumed verifier and authorization code flow directly to the token exchange
  without entering Canvas, A2UI, Activity payloads, or model-visible tools;
- `DirectSignInClient.complete` moves any returned refresh token into IAM's
  `pap.tokenStore` and exposes only an opaque token reference to backend
  capabilities, which use it through `RefreshTokenClient`;
- Preview contributes `pap.browserHandoff` to open the user's trusted browser,
  while the registered Datalayer callback route reconstructs no authority from
  URL parameters beyond passing the full URL to `DirectSignInClient.complete`;
  denial or callback failure requires a new flow rather than reused state; and
- CI must fail any browser artifact that contains the server entry, signing
  key material, raw tokens, assertions, or Session JWT verification code.

## Appspec shape

The Spec, Canvas, and Python editors will round-trip one credential-free model:

```yaml
protocols:
  personal_agent:
    connections:
      - company: example.com
        scopes: [orders:read]          # the company's own scopes
        interfaces: [agent, openapi, mcp]
        extensions: [operations]
  company:
    domain: my-app.apps.datalayer.ai
    interfaces: [agent, mcp]
    signed_out: true
    scopes: [orders:read, orders:write]
    extensions: [operations]
```

Endpoints, client IDs, resources, discovery documents, keys, and deployment
metadata are generated or resolved at ship time rather than stored in the spec.

## Rules and Operations

Studio evaluates its rule before it sends a request that can return a PAP
operation. **Do it** still requires company scope and fixed safety constraints.
**Do it if I asked** requires a live structured grant covering the exact action.
**Ask me first** checks with the person before the request. **Leave it to me**
never sends it.

No rule approves an operation. Every operation the company returns goes to the
person through `pap.approvalSurface`, with the company's summary, structured
terms, cost, expiry, company, operation ID, and revision, and only explicit
approval of the current revision is valid. A new revision invalidates earlier
approval. The operation ID and revision become part of the Studio audit record.

## Studio surfaces

- **Build:** PAP Appspec fields, verified Connections, scope/rule mapping, and
  company policy controls.
- **Preview:** signed-out state, human-completed sign-in, requested/granted/
  missing scopes, responder identity, conversations, and disconnect. The UI
  receives only safe status and opaque handles; callback URLs, codes, PKCE
  verifiers, assertions, Session JWTs, and tokens remain backend-only.
- **Validate:** discovery, identity, sign-in, interface, conversation,
  operations, secret, replay, rate-limit, tenant, and Appspec tests.
- **Ship and Activity:** domain health gates, public metadata, verification,
  Pause/Revoke/rollback, and safe protocol event filters.

Two SDK contracts serve these surfaces. A Python Studio host registers the
`pap` plugin in its Reactor and runs the [live-session
actions](/guides/cli/#live-session-actions) from its palette with
`execute_command` — the same implementation a REPL's slash commands and
`pap commands run` invoke — and contributes its confirmation dialog as the
`pap.approvalSurface`, without which ending a Session or signing out is
refused. Activity's protocol events can come from a
`pap.telemetry` sink: one [allowlisted event](/guides/telemetry/) per
protocol stage, in either SDK, safe to store and display because no
credential or identifier can be in it.
